# Guidelines

Правила поведения против типичных ошибок LLM при работе с кодом. Основано на
[наблюдениях Андрея Карпатого](https://x.com/karpathy/status/2015883857489522876).

**Компромисс:** правила смещают баланс в сторону осторожности, а не скорости.
Для мелких задач — по ситуации.

## 1. Думать до кода

**Не додумывать. Не прятать непонимание. Показывать развилки.**

- Проговаривай допущения явно. Не уверен — спроси.
- Есть несколько прочтений задачи — покажи их, а не выбирай молча.
- Есть способ проще — скажи. Возражай, когда есть основания.
- Что-то неясно — остановись, назови что именно, спроси.

## 2. Сначала простое

**Минимум кода, решающий задачу. Ничего впрок.**

- Никаких возможностей сверх запрошенного.
- Никаких абстракций ради одного места использования.
- Никакой «гибкости» и «настраиваемости», которых не просили.
- Никакой обработки невозможных ситуаций.
- Написал 200 строк там, где хватило бы 50 — перепиши.

Проверка: «сеньор сказал бы, что это переусложнено?» Если да — упрощай.

## 3. Хирургические правки

**Трогать только необходимое. Убирать за собой, не за другими.**

- Не «улучшать» соседний код, комментарии и форматирование.
- Не рефакторить то, что не сломано.
- Держаться существующего стиля, даже если сам написал бы иначе.
- Заметил неиспользуемый код рядом — скажи, но не удаляй.

Когда твои правки осиротили что-то — импорты, переменные, функции, ставшие
ненужными **из-за твоего изменения**, — убери их. Чужой мёртвый код не трогай.

Проверка: каждая изменённая строка должна прослеживаться к просьбе пользователя.

## 4. Проверяемый результат

**Определить критерий успеха. Крутиться, пока не выполнен.**

Превращай задачу в проверяемую цель:
- «добавь валидацию» → «тест на невалидный ввод падает, потом проходит»
- «почини баг» → «тест воспроизводит баг, потом зеленеет»
- «отрефактори X» → «тесты проходят до и после»

Для многошаговых задач — короткий план с проверкой на каждом шаге:
```
1. [шаг] → проверка: [чем убедился]
2. [шаг] → проверка: [чем убедился]
```

### Чем проверять в этом проекте

Порядок от дешёвого к дорогому — не пропускать ступени:

```bash
# 1. Типы и тесты (backend)
docker exec amnezia-panel-backend sh -c 'cd /app && npx tsc --noEmit && npm test'

# 2. Типы (frontend) — на хосте нет node, гоняем в одноразовом контейнере
docker run --rm -v $PWD/frontend:/src:ro -w /app node:20-alpine sh -c \
  'cp -r /src/. /app && npm install --silent && npx tsc --noEmit'

# 3. Деплой — правка в рабочем дереве это ещё не работающая система
docker compose up -d --build backend frontend
docker exec amnezia-panel-backend wget -qO- http://localhost:3001/api/health
```

«Typecheck прошёл» — не критерий успеха для изменения поведения. Оно проверяется
либо тестом на чистой функции, либо реальным вызовом на живой системе.
